Four-process timeline & wire flow

Companion to gear_sonic/scripts/run_x2_quest3_planner_stack.sh. Log files under --log-dir (default): deploy.log, planner.log or vla_bridge.log, manager.log, recorder.log. Horizontal axis is bring-up order (not wall-clock scale): gaps on pose (:5556) starve the sim subscriber; non-empty but inconsistent reference can still look like a “drop” after handoff — see note at bottom.

Spawn order: manager → live_vla_publish_motion_token → recorder → deploy. VLA bridge binds body_pose PUB early; model load may still take minutes after the bind marker.

“Something on the wire” vs “healthy tracking”. An empty or stalled pose stream on :5556 is the classic reason the subscriber sees no fresh reference frames and the stack can go slack. If packets arrive but joint_pos_mj / root do not track the sim, the policy can still diverge after band release — that is a consistency issue, not a silent socket.

How to use this with real logs

Align four terminals: tail -f log-dir/deploy.log (and the other three per mode). When debugging a drop, check whether recorder stopped PUBing (upstream planner/VLA died), whether the VLA pub tick lines freeze, or whether deploy stopped emitting x2_debug (bridge / container exit).
