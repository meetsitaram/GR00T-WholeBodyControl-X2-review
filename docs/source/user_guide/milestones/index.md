| 2026-06-08 | Pose-proxy fallback ladder: freeze arms on upstream stall | **Real X2 + SONIC + VR teleop** | Replaces the PC2 pose proxy's binary `LIVE/IDLE` fallback with a staged `LIVE -> HOLD -> BLEND -> IDLE_CLIP` ladder so a WiFi blip / laptop GC pause / Cursor reload during teleop no longer slams the arms into default-stand. HOLD (default 10 s) re-publishes the LAST forwarded upstream BYTES verbatim -> deploy sees `jvel=0`, zero kinematic surprise. BLEND (default 3 s) lerps `joint_pos_mj` toward the baked idle clip so the eventual fall-back is a smooth glide rather than a step. New `--idle-mode {blend,hold-last,idle-stand}` CLI knob (default `blend`); `idle-stand` reproduces pre-2026-06-08 behaviour as a regression escape. | 2026-06-10 | Closed-loop tracking feedback on the VLA wire | **Real X2 + SONIC + N1.7 VLA bridge** | Adds optional per-arm-joint closed-loop tracking feedback to the VLA bridge wire step cap to stop the open-loop drift / battery-sag / motor-temp oscillations that the v3 static defaults (LPF / blend / scalar step-cap) couldn't reliably suppress. New `_clamp_vector_step_per_joint` clamps each joint independently (vs scalar variant's whole-vector scale) so only the lagging joint slows down. Step 2 (separate commit) will flip default ON and relax v3 statics. | 2026-06-23 | Pose PUB LAN isolation (sim runs can't reach PC2) | **Sim + real X2**, all launchers | Plugs a silent safety leak where sim-mode runs of `run_x2_vla_runtime.sh` / `run_x2_replay_stack.sh` could unintentionally drive the real robot. PC2's `x2_pose_proxy` daemon is always-on by design (operator never SSHes in to stop it) and SUBs `<LAPTOP_IP>:5556` over wifi. ZMQ SUBs connect out, so whenever the laptop bound the pose PUB on `*:5556` (hardcoded everywhere), PC2 attached and the real robot executed the sim wire. The wrapper's `SIM_MODE=1` / `PC2_HOST=""` was internal state that never propagated to the bind argument. Fix: new `PUB_BIND_HOST` env var derived from `SIM_MODE` (runtime) / `PC2_HOST` (replay) — sim → `127.0.0.1`, real → `*`. Plumbed into the bridge, mux, recorder, and replay PUBs. New banner line in both wrappers echoes the resolved bind with LAN-isolation vs LAN-visible suffix. `:=` form so an explicit `PUB_BIND_HOST=*` env override still wins for cross-host sim debugging. Restores the invariant: `--pc2-host` is the single source of truth for whether the laptop's pose wire reaches the real robot. 10/10 new tests + 29/29 existing launcher tests green. |
| 2026-06-23 | VLA bridge holds last-good live `root_quat` across `x2_debug` stalls | **Real X2 + SONIC + N1.7 VLA bridge** | Fixes a regression of the [2026-06-07 heading-stability symptom](2026-06-07_vla_bridge_heading_stability_and_head_lock.md): robot snaps back to spawn heading on first VLA start and on every manual nudge, even though `x2_debug` is being subscribed to. Root cause: the bridge's yaw-rebase + waist_yaw pin were gated on `deploy_fresh` (1 s freshness); on the `not deploy_fresh` branch the wire shipped the baked-identity quat from the idle clip (= world +X), and the C++ deploy commanded the body back to spawn heading on every >1 s wifi blip / GPU stall. Quest3 / VR teleop is structurally protected from this because the kplanner uses "hold last good, overwrite when fresh" semantics on `current_root_wxyz` (`x2_kplanner.py:2816-2821`). Lift that pattern into the bridge: cache `last_known_base_quat_wxyz` + `last_known_body_q_mj`, resolve the source via `_resolve_wire_rebase_source` each tick (`live` / `cached` / `none`), prefer the live snapshot, fall back to the cache, only fall back to identity if no `x2_debug` has ever arrived. A stale cached yaw is strictly better than identity. Promote the one-shot `yaw_rebase_logged` flag to a state-transition emitter (`_log_rebase_source_transition`) so ACTIVE / STALE / RECOVERED edges are each logged once — no per-tick spam, no silent mid-session regressions. The recorder's identical-shape `_compute_idle_root_quat_xyzw` is documented as a dormant bug not fixed this turn (only triggers during recorder-generated idle frames, which haven't bitten in a long time). 25/25 new tests green. **✅ Real-robot validated same day.** |
| 2026-06-23 | BLEND future-window continuity + faster HOLD timeout | **Real X2 + sim**, PC2 pose watchdog | Operator-reported follow-up to the [2026-06-08 fallback-ladder milestone](2026-06-08_arm_freeze_on_upstream_stall.md): on Ctrl+C of a VLA run, after ~10 s of stillness the robot arms snap to a different pose then smoothly settle. Diagnosis: the snap was happening at the HOLD → BLEND boundary, where the watchdog kept `joint_pos_mj` continuous (lerp α=0) but switched `joint_pos_mj_future`, `root_quat_xyzw_future`, `joint_vel_mj_future`, `motion_token`, and hand fields from the cached VLA values to idle-clip values / zeros in one tick. The C++ deploy integrates the full future window + motion_token, so the policy's planning horizon reshaped in one tick → shoulder/elbow snap. Wrists were exempt because `--wrist-bypass ik` routes them directly from the wire. Fix: snapshot `joint_pos_mj_future` / `root_quat_xyzw_future` / `joint_vel_mj_future` / `motion_token` at every fresh upstream tick; lerp all of them against the (yaw-rebased) idle clip values across BLEND with the same α as the current jpos. `build_idle_frame_msg` gains four optional override kwargs; quat futures use a new numpy-only `nlerp_quat_arrays_xyzw` helper (scipy-free PC2 budget). Legacy v4 upstreams that never set futures gracefully retain today's snap on the absent fields only — no regression. **Hands deliberately out of scope** (operator confirmed they don't matter here; same cache+lerp pattern would apply if revisited). Also reduces the `POSE_PROXY_HOLD_LAST_SECS` default from `10.0` to `5.0` in all three config sources so intentional Ctrl+C reaches the smooth BLEND ramp roughly twice as fast (~5.3 s instead of ~10.3 s of frozen VLA pose before motion). Operators wanting the old window: `export POSE_PROXY_HOLD_LAST_SECS=10.0`. 28 new pure-pytest unit tests + 1 updated default-pin; 49/49 pose-pipeline tests green. **PC2 deploy + watchdog restart owned by operator** — the assistant deliberately didn't touch PC2; sim picks up the new code immediately. Long-form architectural story at [`x2_blend_future_window_continuity`](../../references/x2_blend_future_window_continuity.md). |

| 2026-06-24 | PC2 pose watchdog HOLD state yaw-rebases cached frames | **Real X2**, PC2 pose watchdog | Operator-reported follow-up to [2026-06-23 BLEND future-window continuity](2026-06-23_blend_future_window_continuity.md): on Ctrl+C of `run_x2_pkl_direct_stack.sh --pc2-host …` the robot "tries going back to previous locked position abruptly" for the full 5 s HOLD window before BLEND/IDLE_CLIP take over. Falls back to verbatim re-publish if `x2_debug` is stale (`--x2-debug-max-age-s`, default 0.5 s) or the splice fails (legacy v4 header missing the field). Watchdog adds a `hold_frames_with_rebase` counter (`hold_rebased=N` in status lines) plus three one-shot ACTIVE / FALLBACK / splice-FAILED log lines mirroring the recorder's idle yaw-rebase gates. Startup banner gains an `HOLD yaw-rebase: ENABLED / DISABLED` line. 5 new unit tests; 25/25 fallback-ladder tests + 93/93 broader pose-pipeline regression sweep green. **`--hold-last-secs` default unchanged** (5.0 s remains right-sized now that HOLD doesn't pin yaw).
